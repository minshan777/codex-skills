# 页面用例与自动化的边界

仅在用户明确要求用例适合 Playwright 执行、或检查既有用例的自动化准备时读取。本技能只编写用例，不执行测试，也不改动执行工程。

## 产品用例优先

- 主表依然只写页面上能查看的条件、用户能完成的操作和能看到的结果。脚本怎么找按钮、等待页面、模拟错误、清理数据，都属于自动化工程，不写进七列用例。
- 遵循当前工作区的执行约定；必要时只读查看指定工程 README 和已有脚本，判断哪些页面已有支持。不要因为没有脚本就给正常产品用例添加“缺少定位器”“需要后台控制”等前置条件。
- 不把工程中的账号代号、执行命令、工具检查、代码参数和实现术语复制进用例。多成员验证写明实际产品权限和切换成员后的访问动作，不能用同一真实账号冒充不同成员。
- 不将自动化工具能力当作产品规则。例如页面本来允许直接创建角色，就直接写创建操作；不能为了稳定观察生成中状态，先要求服务器暂停处理。

## 让步骤清楚，但不塞入脚本说明

- 按实际页面给出入口、字段和按钮。多个同名按钮用所在弹窗、记录名称或列表行区分，不要求读者理解选择器。
- 等待以页面结果为准，例如“等待卡片生成完成”“等待保存提示出现”。不写固定睡眠时长或“释放事件”。只有产品明确规定处理时限时，才把它写成验收标准。
- 数据用具体名称，步骤复用同一名称。避免重名的技术处理由执行脚本完成；不在每行铺陈运行标识算法。
- 涉及刷新、再次打开、另一成员查看时，把用户动作写完整。图片内容或音色需人工判断时直说“人工核对”，不要假装按钮变为可用就证明内容正确。

## 异常状态和短暂状态

- 对页面已有的失败记录，可写“前置条件：有一个生成失败且可重试的角色”，按页面完成重试。没有现成数据时标明“【待准备】”，不伪称已有。
- 正常流程中的生成中状态直接在提交后观察。若生成太快没有观察到，执行时只说明该检查点未观察到，不凭空增加“后台挂起”的前置条件，也不因此把创建功能判为失败。
- 页面上没有入口、也无法通过正常操作准备的异常，不改造成必执行页面用例。需要内部故障模拟或伪造状态才能验证的风险，交付时简述为待确认事项；除非用户另外明确要求技术专项测试，否则不放入主表。
- 若用户另外要求模拟页面或组件测试，需单独说明它只验证模拟条件下的页面表现，不能代替真实保存、扣费或权限结果；不要将这类测试混入默认产品用例。

## 重复执行与结果说明

- 需要清理或恢复时，用产品动作表达，例如“测试结束后删除本次新建角色”“把项目名称改回原值”。只在有必要的场景说明，不给每行追加成段统一清理模板。
- 写用例不授权实际购买、邀请或修改共享数据；执行时按用户授权和工程约定处理。
- 编写阶段没有执行结果。交付只说明写了哪些页面场景，以及哪些页面数据尚未准备，不保证全部可自动运行。
- 执行限制向用户也用产品语言：如“当前没有生成失败的角色，暂时无法检查重试按钮”。技术原因只有用户追问或需要作出技术决定时再解释。
