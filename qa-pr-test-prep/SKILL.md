# PR 测试前置准备

将“准备测试这个 PR”视为明确请求以下三项交付，一次完成，默认中文：

1. 大白话解释该 PR 改动了什么。
2. 一份真实可下载的冒烟用例 `.xlsx`。
3. 在回复中直接写出一条用户可以照着操作、确认功能是否部署可用的冒烟用例。

## 触发和范围

- 用户提供 PR 链接、提测任务链接，或在当前对话已明确 PR 后说“准备测试”，均适用。用户只说“查看任务”“解释这个 PR”“准备好了吗”时，不据此生成用例。
- 本触发词已授权生成冒烟用例文档，不再询问是否需要输出；不额外生成全量功能用例、执行报告、覆盖矩阵或独立说明附件。
- 仅准备，不登录产品、不执行测试、不生成站内资产、不扣积分、不修改业务数据、不向任务或 PR 发评论。用户另有执行要求时，按该要求和工作区执行约定处理，不能把准备任务当成执行授权。
- 用户明确缩小交付范围时遵循当次要求，例如“只解释改动”“只给我一条”不强制补齐三项。

## 先确定本次依据

- 优先从当前任务链接和对话确定唯一待测 PR。使用可用连接器读取任务正文、相关评论和关联 PR；连接器缺少能力时使用可用的只读页面方式。已有来源仍适用可复用，不重复全仓扫描。
- 核实 PR 当前状态、最新描述、head 提交及必要改动；结合对应版本的已有实现确认触发条件。不能用其他分支、本地旧代码或历史用例替代当前依据。
- 提测任务缺少细节时从关联 PR 补齐，不能把缺少任务说明等同于缺少全部需求。有明确来源才描述规则、按钮、费用、权限和结果。
- 区分需求说明、当前实现和开发者自测记录。开发者说“已部署”“自测通过”只作为来源信息，不宣称本次已确认部署或测试通过；需求与实现不一致时说明待确认，不自行改写验收标准。
- 无法确定 PR 时才询问链接或编号。来源不可访问时说明缺口，请用户提供可访问来源或必要内容；不能凭标题猜出完整用例或伪造文件。

## 交付一：大白话解释

- 先用一句话说清这次给用户增加或改变了什么，再按实际改动概括：从哪里进入、能做什么、操作后看到什么、关键限制或费用、谁能使用。
- 同时覆盖本次直接影响的关联行为，例如入口切换、历史记录、重新生成或权限分支；不把技术重构描述成额外产品能力。
- 用页面和用户动作解释，避免展开内部接口、服务、队列和代码文件。只在帮助理解测试条件时保留必要技术名称。
- 明确当前开放条件及重要排除项，但不机械堆砌无关限制。PR 包含早期描述和后续补充时，按最新范围合并说明。
- 链接到已读取的 PR 或任务作为依据，不把开发自测、推测或文档准备结果写成自己的执行结论。

## 交付二：冒烟用例文档

- 使用同目录安装的 [qa-smoke-cases](../qa-smoke-cases/SKILL.md) 技能，并遵循当前可用的 Spreadsheets 技能完成生成、导出、内容校验和视觉检查。依赖路径变动时从当前技能目录发现，不写死运行时版本。
- 依据本次 PR 重新筛选最少且足够的场景，覆盖新增或修改的核心动作、必要分支和明确变化；不直接缩抄全量用例，不预设条数。
- 只使用一个“测试用例”工作表，固定七列：用例编号、用例标题、前置条件、输入数据、操作步骤、预期结果、优先级。具体写法、排版、编号和文件命名遵循 qa-smoke-cases。
- 用产品语言写真实页面可执行和可判断的场景。测试账号、素材或历史记录尚未核实时标“【待准备】”，不声称资产已生成；需求含糊用“待确认”在回复中说明，不列为必过用例。
- 准备阶段不因缺少执行账号或资产而删掉已确认的权限分支，也不能拿一个身份冒充多个身份。说明执行数据缺口即可，不自动申请账号或改动权限。
- 返回实际文件链接，简短说明条数、覆盖重点及必要缺口，并明确“已编写，未执行”。

## 交付三：一条手动部署验证用例

- 从本次冒烟文档中选择一条识别度高、步骤少、操作成本低的核心场景，在回复中完整展开；保留对应 TC 编号，避免创造另一套相互矛盾的预期。
- 必须能区分本次新行为与旧版本。仅“首页可打开”“已登录”“入口存在”通常不够；根据 PR 选择具体变更后的操作及可观察结果。用户已要求的核心新增动作不能被入口检查替代。
- 优先选择低成本且可恢复的流程。同样能识别改动时选更便捷的操作；确需生成才写生成动作，并注明已确认的站内积分费用，不为验证部署引入购买、真实付款或订阅变更。
- 写明标题、必要前置条件、具体输入、编号步骤、预期结果。使用已核实的入口和按钮名称；有账号开放条件时写清，避免用户因未开放而误判未部署。
- 环境、账号优先沿用用户当次要求及工作区 AGENTS.md；已有上下文先自行读取。未确定环境时用明确的“待测环境”，不擅自选择生产；不要写入密码或令牌。
- 用一句话说明判断边界：通过表示本次特征对应的功能链路部署可用，不证明精确提交 SHA 或全部改动通过。失败时保留账号/权限、环境和产品问题的可能性，不一律归因为未部署。

## 最终检查

- 回复按“改动解释 → 冒烟文档 → 一条手动用例”组织，三项均有实质内容，不只提出计划或让用户再问一轮。
- Excel 可下载且经过校验；手动用例能独立照做，和文档中同编号场景一致。
- 对未确认要求、待准备数据和未执行状态如实说明。保持简洁，不额外输出构建脚本、预览或内部支持文件。
