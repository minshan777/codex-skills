# PR 冒烟用例 Excel

交付真实可下载的 `.xlsx` 文档。以最少且足够的功能场景，覆盖当前 PR 已确认的新增或修改行为；有待确认项时明确说明覆盖缺口，不声称已完整覆盖。默认中文。

## 触发与边界

- 用户说“输出冒烟用例”时使用本技能；即使当前已有普通测试用例，也按冒烟范围重新筛选，不直接照搬全量用例。
- “输出测试用例”等普通请求由通用用例技能处理；本技能的明确冒烟请求优先于通用用例流程。
- “做冒烟测试”“执行用例”属于实际执行任务，不因本技能而只输出文档。本技能也不主动登录、执行、生成产品资产或修改业务数据。
- 输出冒烟用例不是只写一条部署确认，也不是只写一个正常流程。覆盖数量由本次改动决定，不设固定条数，不为凑数加场景。

## 编写前：先核实边界和已有条件

- 核实当前 PR 的版本、最新需求说明、验收要求和明确排除项；读取对应提交的必要改动及相关已有实现，不能把本地其他分支、历史描述或旧用例当作当前依据。已有足够且仍适用的证据可复用，无需重复全仓审查或执行测试。
- 对每项拟覆盖的变化，在内部整理“需求依据 → 适用条件 → 用户操作 → 可观察结果 → 对应用例”。需求依据保留可定位的来源及版本；区分本次新增/修改、沿用的已有行为和明确不包含的能力。此记录用于写作与查漏，不额外增加 Excel 列、工作表或附件。
- 核实会改变结果的已有功能条件，如对象是否已有内容、权限、当前选择、修改范围、历史记录保留方式，以及页面是否真的提供所需入口。把必要且可从页面核对的条件写进前置条件，不把有条件的行为改写成无条件保证。
- 需求与实现分开判断：用户明确要求、已确认的产品需求和验收说明用于确定应有行为；代码、测试和页面用于核实已有条件及当前实现。代码或测试中的某个现象不自动成为产品需求，也不能为了匹配实现而删减明确需求。发现冲突，记录为“待确认：需求与当前实现不一致”，保留双方依据，不自行裁决为产品缺陷或改写验收标准。
- 必须分清“已确认需求”“已核实的已有条件”和“推测/待确认项”。不能把常见产品习惯、理想体验、PR 标题的概括描述或模型推导直接升级为要求；代码已支持的其他能力也不自动进入本次冒烟范围。
- 检查承诺的粒度：一次操作、一次有效修改、一轮聊天和整个故事不是同一个范围。例如，PR 只保证最近一次有效修改可撤销，就不能写整轮聊天的全部修改一次撤销；在输入中要求“作为一次修改完成”也不能替产品新增该保证。若锁定只适用于已有镜头的故事，应明确该条件，不能据此要求空故事也锁定。这些例子只说明核实方法，不作为其他 PR 的固定规则。

## 无明确依据的要求如何处理

- 对范围、前置条件、页面入口或预期结果缺少依据的要求，标为“待确认”，简述不确定点与需要确认的具体行为；不以确定口吻写成预期结果，不纳入必过验收项或已覆盖统计。
- 默认在交付消息中单列简短的“待确认”清单，不把未确认的要求混入正式用例主表；仍按七列输出已确认范围的 Excel。不要新增待确认工作表或状态列，除非用户要求。
- “【待准备】”只用于产品规则已明确、但尚缺测试账号或资产等数据的情况；不能用它掩盖需求含糊。例如，缺少可编辑故事是待准备，不知道是否支持整轮撤销是待确认。
- 部分内容不明确时，先完成有依据的用例并说明剩余缺口。若连核心功能或验收结果都无法确定，先提出具体澄清问题，不编造一份看似完整的验收表。

## 从已确认边界确定最小完整范围

1. 优先读取当前对话中明确的 PR、需求和提测说明；通过可用连接器读取 PR 的最新描述和必要改动。只有无法确定当前待测 PR 或功能范围时才询问。不能用历史 PR 默认替代当前任务。
2. 使用上述已核实的覆盖关系筛选用例；每条预期结果均须能追溯到明确的需求依据，并包含必要的已有功能条件。
3. 只收入与本次变化有直接关系的功能场景：新增入口、修改后的核心流程，以及 PR 明确改变的结果、限制或必要分支。每条都应能回答“漏掉这条，会漏验 PR 的哪项功能变化？”回答不清就删除。
4. 核心新增/修改动作必须实际操作并检查结果，不能只检查入口出现或成功提示。例如本次增加聊天修改故事，就发送具体修改内容，再打开相应故事检查实际内容；若新增撤销与重做，两种动作都需验证。
5. PR 明确包含不同权限、实验分组或开关两侧行为时，保留能确认这些差异的最少必要场景。没有这些变更时不自动加权限、对照组等用例。
6. 不自动扩展至通用登录、普通问答、全面回归、浏览器兼容、性能、压力、安全攻击、穷举边界、无关异常或页面样式。若其中某项本身就是 PR 的改动，则只验证该项具体变化。
7. 同一次操作可顺带验证的直接结果合并为完整场景；需要不同条件、独立动作或互斥结果的分支分开。不能为少写条数把所有流程塞进一条，也不能将同一结果机械拆分。
8. 不将执行现场的临时阻塞或猜测写成产品验收要求；不把前置数据“待准备”写成已有数据。若 PR 涉及的功能不能从产品页面操作或验证，在交付消息简短说明缺口，不编造页面用例。

## 产品语言要求

- 读者不需要懂代码，也能知道在哪个页面、对哪个对象、输入什么、做什么，以及应看到什么。使用已核实的页面名称、按钮和产品词汇，句子简短。
- PR 和代码仅用于理解变化，不把接口、字段名、服务、数据库、事件、队列、SSE、worker、fixture、Mock、定位器、回调、快照、provenance 等实现词抄进用例。页面本身的专有名称可保留，但不拿技术结论代替页面结果。
- 写“只有查看权限的成员不能修改故事”，不写“服务端鉴权拒绝 command”；写“本轮回复下出现撤销按钮”，不写“绑定 reply provenance”；写“刷新后仍显示新名称”，不写“持久化成功”。
- 前置条件只能是产品页面可核对或通过正常使用可准备的条件；步骤只能是页面操作；预期结果必须能从页面内容、控件状态、重新打开或刷新后直接比较。
- 明确对象、测试输入和结果。不写“功能正常”“数据正确”“检查权限”等空泛描述，也不以聊天宣称“修改成功”代替目标对象的实际变化。
- 不假设 PR 中的内部字段对应页面上的可编辑属性。先核实产品是否有该内容及查看入口；不确定时说明待确认，不虚构“镜头描述”等不存在或无法查看的控件。
- 不加入检查接口、控制后台、查询日志或人为注入故障的步骤。只编写用例时不声称资产已准备、环境已部署或测试已通过。

## 固定 Excel 格式

默认只有一个工作表，名称为“测试用例”，从 A1 开始，严格七列：

| 列 | 要求 |
| --- | --- |
| 用例编号 | 文本 `TC-001` 起，唯一、连续；修订已有文件时保留原编号。 |
| 用例标题 | 主要动作 + 具体产品结果，避免只有功能名。 |
| 前置条件 | 本例必要的可见条件，如可编辑故事、只读成员、已确认启用该功能的账号。省略通用登录和部署条件；无特殊条件真正留空。未有数据简短标“【待准备】”。 |
| 输入数据 | 具体可复现的填写值、选择项或必要素材；没有则填“无”。不放密码、令牌或内部配置。 |
| 操作步骤 | 用 `1. `、`2. ` 编号，真实换行；写出页面入口、对象、用户动作，以及验证需要的重开或刷新操作。 |
| 预期结果 | 写可直接比较的实际内容或按钮状态；对应本条步骤；不要只有成功提示。 |
| 优先级 | 仅 P0、P1、P2。核心新增流程及明确的发布阻断风险为 P0；主要修改和必要分支为 P1；确有直接关系的次要变化为 P2。不全部强设 P0。 |

不增加执行状态、实际结果、来源、技术准备等列，不增加覆盖矩阵或测试报告工作表；用户本次明确指定其他格式时遵循用户要求。

## 生成、检查与交付

- 创建 Excel 时读取并遵循当前可用的 Spreadsheets 技能，生成、导出、校验并视觉检查真实 `.xlsx` 文件。
- 冻结首行、启用筛选、正文顶部对齐并自动换行；步骤与预期列适当加宽，按内容调整行高，确保完整可读。数据区域不合并单元格、不插空行。
- 导出前逐条反查：每个“必须、全部、始终、自动、一次”等确定性承诺是否有依据？是否遗漏触发条件、扩大修改或撤销范围？每条预期能否追溯到当前 PR 的已确认要求？无依据的内容移入待确认清单，不保留为必过预期。
- 同时审阅：与 PR 是否直接相关？已确认的变化是否覆盖齐全？产品人员能否照着做并判断结果？有无技术术语、虚构入口或重复场景？若仍有未确认范围，不宣称完整验收覆盖。
- 校验七列表头、编号唯一、必要内容完整、优先级有效和步骤真实换行；不把预检或执行结果填进用例。
- 文件命名为 `<PR编号或功能名>_冒烟用例_<YYYYMMDD>.xlsx`，使用用户当地日期，保存到本次可写输出目录并返回可点击文件链接。
- 交付消息简短说明条数、直接覆盖的已确认功能，以及必要的待准备数据或待确认要求；明确为已编写的用例，未实际执行。来源链接放在消息中，不额外输出用户未请求的附件。
